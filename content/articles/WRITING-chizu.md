# 「課題の攻略地図」記事（chizu型）の書き方

1つの困りごとタグを対象に、事例群から**どんな手の入れ方があるか**を整理し、解決策の全体像を渡すフォーマット。

企画の起点は、**「同じ悩みの事例を並べたら、解き方は何通りに分かれたか」**。

wakaremichi型が2社の分岐の理由を読み、genba型が1社を深く読むのに対し、chizu型は**入口の記事**である。dounyumae型で自分の悩みに気づいた読者が、次に「どんな解き方があるのか」を知り、その先で各ルートの比較記事・個別事例へ進む——既存の型をつなぐ位置に置く。

## 0. この記事の性質と限界

- ルートの分類は**編集部の整理**であり、市場の全選択肢の網羅ではない。網羅したように書かない（テンプレートのポリシー表記にも明示される）。
- 掲載事例から言えるのは「この道を採った会社が掲載されている」ことまで。**ルート間の優劣や、各ルートの一般的な成功率は導けない。**
- 各ルートは多くの場合**併用できる**。排他の選択肢として描かない。

## 1. テーマ（タグ）を選ぶ

- 該当事例が十分にあり（目安50件以上）、**解き方が実際に複数に分かれている**こと。1つの解き方に集中しているタグでは地図にならない。
- 業種の広がりがあること。
- ルート分けを「業務のどこを変える道か」で説明できる程度に、施策（actions）の記述が具体的な事例が多いこと。

## 2. 全件を読み、ルートを立てる（この型の中心工程）

該当事例の challengeDetail / actions を**全件**読む。ここを済ませずにルートを立てない。

### ルート分けの原則

- **製品カテゴリで分けない。「業務のどこを変える道か」で分ける。** 同じカテゴリでも変えた場所が違えば別ルート、違うカテゴリでも変えた場所が同じなら同ルートになりうる。
- ルートの数は材料に合わせる（3〜5本が目安）。見出しを揃えるために作らない。
- **タグの中の「範囲外」を正直に切る。** 同じタグでも悩みの中身が違う事例群（例:「転記」タグの中の「配布の手作業」）は、`scopeNote` で輪郭を引いて除外を明示する。黙って混ぜない・黙って捨てない。
- 分類に迷う事例が多数残るなら、タグの選定かルートの切り方を見直す。

### 代表事例の選び方

各ルートに2〜3件。次を満たすものを選ぶ。

- そのルートの「変えた場所」が施策の記述から確認できる。
- 課題・施策・成果が具体的（数値成果があることが望ましい）。
- ルート内で業種や規模が散っていると、読者が自分に引きつけやすい。

body に書く事実（数字・工程）は、**必ず事例本文と照合する**。事例に書かれていない仕組みの説明を補わない。

## 3. 構成

扉（題字・タグ・タイトル・リード）
→ サムネイル（任意）
→ 目次
→ 一 この悩みの輪郭（scopeNote）
→ 二 手の入れ方の地図（routes ＋ 代表事例 ＋ 分布の参考枠）
→ 三 自社ではどこから調べるか（startPoints）
→ 結び（closing）＋ タグページへの導線
→ ポリシー表記

該当件数・業種数・解き方カテゴリの内訳は、テンプレートが axisTag から自動集計する（範囲明示つきの参考情報。ルートの根拠や優劣の証拠には使わない）。

## 4. 執筆の作法

### 1. ルートの名前は「動かす場所」が見える動詞にする

「AI-OCR活用」ではなく「届いた紙を機械に読ませる」。製品側でなく業務側の言葉で名付ける。

### 2. 各ルートの body は、代表事例の事実で書く

そのルートの一般論ではなく、代表事例が実際に変えた工程と数字で説明する。数字は対象・期間が分かる書き方を保つ。

### 3. 併用と限界を必ず書く

`routesNote` で、（1）ルートは併用できること（実例があれば挙げる）、（2）優劣は事例からは言えないこと、を断る。

### 4. 「どこから調べるか」は診断ではなく手順

startPoints は「あなたはルート◯だ」と判定させる質問にしない。自社の転記・悩みを観察する手順（書き出す・確かめる・数える）として書き、どのルートを調べる候補になるかの目安にとどめる。

### 5. 入口記事としての導線を張る

各ルートは代表事例へ、結びはタグページへつなぐ。関連する wakaremichi / genba 記事があれば本文から言及してよい（そのルートの分岐を深掘りする記事として）。

## 5. 公開前の編集チェック

- 全件を読んでからルートを立てたか。
- ルートが製品カテゴリの言い換えになっていないか（業務の変更箇所で分かれているか）。
- scopeNote で対象の輪郭（除外した事例群を含む）を示したか。
- 代表事例の数字・工程が本文と一致するか。
- ルートを排他の選択肢として描いていないか。併用の断りがあるか。
- 優劣・成功率・網羅を示唆する表現がないか。
- startPoints が特定ルートへの誘導や適合診断になっていないか。

## 6. 公開手順

基本手順は [WRITING-wakaremichi.md](WRITING-wakaremichi.md) と同じ。

1. `python -c "import uuid; print(uuid.uuid4())"` で slug を生成する。
2. `content/articles/<uuid>.json` を作成する。`format` は `"chizu"`、`no` は連番とする。
3. サムネイル（5:3）を `public/thumbnail/<no>.png` に置き、`thumbnail` にパスを書く（未設定でも可。chizu型は事例画像への自動フォールバックがない）。
4. `npm run build` でビルドが通ることを確認する。
5. プレビューで、ルート・代表事例リンク・自動集計の件数・タグ導線を確認する。
