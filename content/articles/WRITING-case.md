# 事例記事（/cases/…）の書き方

事例記事は**カルテであって、読み物ではない**。答える問いは1つ——「この会社は、何に困り、何を導入し、どう改善したか」。

**事例の説明はさらっとでいい。** 深掘り・読み・比較は事例セレクション（記事）の仕事で、詳細は原典の仕事。事例記事は両者への入口として、事実の骨だけを短く置く。

## 生成の仕組み

事例記事は手書きではなく、収集パイプラインが原典から構造化抽出する（`/collect-cases`）。

| 工程 | 担当 |
| --- | --- |
| 原典 → 構造化データ（title/summary/課題/施策/成果） | `extract_cases.py`（Claude Haiku 4.5） |
| 成果と規模の分類（「設置28カ所」は成果でなく規模） | `fix_results.py` |
| 困りごとタグ付け | `tag_cases.py`（既存語彙に寄せる。既存タグは変えない） |

人が書くのは、**間違いを直すとき**だけ（下記「手直しのしかた」）。

## 各フィールドの作法（data/cases.json）

| フィールド | 書き方 |
| --- | --- |
| `title` | 何がどう変わったかが分かる一文。原典の見出しを基に、数値成果があれば含める |
| `summary` | **2〜3文・150字以内**。課題→打ち手→成果の骨だけ。修飾語・宣伝文は入れない |
| `challengeDetail` | 導入前の状況。誰が・どの工程で・何に困ったかを、**原典の記述の範囲で**具体的に。解体新書の引用素材になるので、事実だけを書く |
| `actions` | 何を導入し、業務の何を変えたか。製品名だけでなく変えた工程を書く |
| `results` | 原典に明記された成果のみ（metric＋value）。対象・期間・単位を保つ。規模の数字（台数・拠点数・件数）は `scale` へ |
| `tags` | 困りごとタグ。既存語彙（`tag_cases.py` のSEED＋蓄積）に寄せる |

## 共通の作法

* **原典にないことを書かない・盛らない。** 要約で意味を変えない。
* 成果の数字は単位と対象を落とさない（「削減」だけにしない）。
* 「業界No.1」「圧倒的」など原典の宣伝表現は要約時に落とす。
* さらっと＝短さそのものではなく、**カルテの役割を超えない**こと。背景の物語・選定理由の推測・他社比較は書かない（それは記事の仕事）。

## 手直しのしかた

1. `vizlabo_media/data/cases.json` の該当エントリを直接編集する（IDで検索）。
2. `npm run build` で反映を確認する。
3. 注意：同じURLが再抽出されると `merge_cases.py` は抽出側を優先して上書きする（タグは保持される）。恒久的に直したい誤りは、抽出プロンプト側（`extract_cases.py`）の改善も検討する。

## 公開前チェック（手直し時）

* 原典と突き合わせたか（数字・固有名詞・単位）。
* summaryが150字を大きく超えていないか。骨以外が混ざっていないか。
* 成果と規模が混ざっていないか。
* 宣伝表現・推測が残っていないか。
