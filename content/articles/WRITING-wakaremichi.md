# 「分かれ道」記事（wakaremichi型）の書き方

事例解体新書の基本フォーマット。**同じ課題 → 違う解決策 → なぜ分かれたのか**を1本で解く。

企画の起点は、**「事例を並べたら、どんな疑問が生まれたか」**。

複数の事例から見つけた違いを、各社の事情に照らして読む。読者に渡すのは、解決策の優劣ではなく、**自社で選択を考えるための材料**である。

wakaremichi型はスポンサーなしの比較記事として扱う。スポンサーの事例を軸に展開する記事は、別フォーマットで扱う。

フィールドと記事の対応は `README.md`、ペア探しは `jirei_collector/find_pairs.py` を参照する。

## 1. ペアを選ぶ

### 候補を探す

```bash
cd jirei_collector
python3.11.exe find_pairs.py --top 12
```

スコア上位を入口に、次の観点で候補を読む。スコアは探索の補助であり、記事化の判断基準ではない。

* **共有タグ2つ以上を候補の目安にする。** タグの一致だけで「同じ悩み」と判断せず、課題文で確認する。
* **業務のどこに手を入れたかが異なる。** `productCategory` の違いは手がかりだが、必須ではない。同じカテゴリでも、変更した工程や運用が違えば比較できる。
* **原則としてベンダーが異なる。** ただし、ベンダーが違うだけでは分かれ道にならない。
* **両方に具体的な課題・施策・成果の記述がある。** 数値成果があることが望ましいが、数字の有無や大きさだけで選ばない。
* **制約・既存の仕組み・変更できる範囲などに、本文で確認できる違いがある。** 規模や業種の対照は補助材料とし、それ自体を選択理由にしない。

### 問いを1文で書く

候補の2社について、全文を読む。

確認する項目：

```text
title / summary / challengeDetail / actions / results
```

必要に応じて原典も確認し、執筆前に記事の問いを1文で書く。

例：

> 同じ転記の負担を抱えながら、なぜ一方は入力を自動化し、もう一方は転記そのものをなくしたのか。

「A社とB社を比較する」は作業の説明であり、問いではない。**共通する悩みと、説明したい違い**が1文の中にあることを確認する。

### 比較が成立するか確かめる

次の3点を確認する。

1. **悩みは、具体的にどこまで同じか。**
   「紙が多い」などの大きな括りだけでなく、誰が、どの工程で、何に困っていたかを見る。

2. **解き方は、具体的にどこが違うか。**
   製品名ではなく、変えた工程・運用・情報の流れを言葉にする。

3. **その違いを説明する材料が本文にあるか。**
   制約や選定理由、残した仕組みなど、読みの根拠を確認する。

**分かれた理由を本文から推理できないペアは捨てる。** 無理に理由を補うと、記事全体が創作になる。

また、2社が同じ選択肢を比較検討したとは限らない。実際の選定経緯が分からない場合は、編集部が事後的に解き方を比較していることを明確にする。

## 2. 執筆前に、事実と読みを整理する

各論点について、次の3つを分けてメモする。

| 区分            | 書く内容                       |
| ------------- | -------------------------- |
| 本文で確認できる事実    | 課題、実施した施策、明記された選定理由、成果など   |
| 編集部の読み        | 事実同士を結びつけた解釈。根拠となる記述も対応させる |
| 公開情報では分からないこと | 比較した候補、選ばなかった理由、費用、成果の内訳など |

**「その選択が会社の状況に合っている」と「会社がその理由で選んだ」は別である。**

選定理由が明記されていなければ、「〜だから選んだ」とは書かない。「〜という条件に合う選択だったと読める」など、解釈の範囲にとどめる。

「大企業だから基幹を替えられない」「小企業だから身軽」「従業員が少ないからIT専任がいない」といった、属性からの決めつけを根拠にしない。

## 3. 構成

### 基本の流れ

扉（題字・タイトル・リード）
→ サムネイル
→ 目次
→ 対面カルテ（2社を左右に）
→ 同じ悩み
→ 分かれた決断
→ なぜ分かれたか
→ 照合（必要な場合）
→ 今回見えた分岐点
→ あなたの会社なら
→ 結び

### 各パートの役割

**扉**

2社に共通する悩みと、異なる解き方を示す。「なぜ分かれたのか」という問いを提示する。タイトルやリードで、本文より強い断定をしない。

**対面カルテ**

企業・課題・施策・成果を並べ、比較の前提を揃える。規模や業種は背景情報として扱う。

**同じ悩み**

両社の課題文を実文引用し、何が共通していたかを示す。業務の種類など、比較上の重要な違いも隠さない。

**分かれた決断**

各社が業務のどこに手を入れ、何を変えたかを示す。併用可能な解決策を、排他的な二択として描かない。

**なぜ分かれたか**

本文の事実を根拠に、分岐を説明する読みを置く。論点数は材料に合わせ、見出しを埋めるために理由を増やさない。

共通点も調べ、問いへの理解を深めるものがあればここに置く。

**照合（必要な場合）**

第三の事例で、読みが別の状況にも当てはまるか、修正が必要かを確かめる。適切な事例がなければ無理に設けない。

**今回見えた分岐点**

冒頭の問いに、今回の事例から言える範囲で答える。説明できた点と、分からなかった点を整理する。

**あなたの会社なら**

読者が自社を点検するための問いを置く。前段で見えた分岐点に対応させる。

**結び**

今回の発見を短く締める。本文で示していない一般論や、特定の製品を推す結論を追加しない。

### 実装との対応

書くのはJSONの「書かれた部分」だけ。引用・数字・道別リストはビルド時にデータから組まれる。

上記は編集上の構成方針である。フィールドへの割り当ては `README.md` で確認する。

照合の省略や「今回見えた分岐点」の配置にテンプレートが対応していない場合は、スキーマ・テンプレート側の対応が必要になる。必須欄を埋めるために、根拠のない照合や文章を追加しない。

## 4. 執筆の作法

### 0. 見出しは「情景」か「発見の断言」を短く（全型共通）

見出しに使わないもの：

* **カギ括弧の強調**（「変えた場所」が違う）——語を囲んで済ませない。
* **ダッシュの補足**（なぜ分かれたか — 編集部の読み）——説明は本文の仕事。見出しに説明をぶら下げない。
* **講義・作業の口調**（〜で読む、〜を確認する、〜を並べて読む）——読者への指示文にしない。

良い形は、状況が浮かぶ短い文か、発見をそのまま言い切る文。

> 例：その人が休むと、止まる。／二社とも、先に残すものを決めていた。／片方は届いた後、片方は生まれる前。

断言する見出しは、本文がその根拠を持っている範囲でだけ使う（タイトルと同じく、本文より強くしない）。

### 1. 仮説には、根拠と限界を付ける

各「読み」に、根拠となる本文の記述を対応させる。

「〜だと読む」と付けるだけでは、根拠のない推測は成立しない。推理パートにはテンプレートで「編集部の読み」の断り書きを付けるが、本文でも事実と解釈の境界を明確にする。

結論でも、仮説を事実に変えない。

### 2. 重要な反論を、自分から扱う

「この2つは両立するのでは」「出どころより業務の違いでは」など、読みを左右する反論を確認する。

本文では、その記事の結論に関わるものを扱う。反論を列挙するのではなく、認めたうえで何が言えるかを示す。

### 3. 比較の核心は「業務のどこに手を入れたか」

製品名やカテゴリの対決にしない。

入力、受領、照合、承認、保管など、変更した工程を具体化する。必要に応じて、誰の仕事や情報の流れが変わったかまで読む。

### 4. 対比だけでなく、共通点も調べる

異なる選択をした2社にも、残した仕組みや導入の進め方に共通点があるかもしれない。

問いへの理解を深める共通点があれば本文に置く。毎回「実は同じだった」と結ぶ必要はない。

### 5. 第三の事例は「検証」ではなく「照合」

第三の事例は、仮説を補強するものだけでなく、修正を迫りそうなものも探す。

* 似た条件なのに、違う道を選んだ会社
* 異なる条件なのに、同じ道を選んだ会社
* 2つの道を併用している会社

一致する事例が増えても、原因を確かめたことにはならない。照合の結果、どこまで読みが通じ、どこからは分からないかを具体的に書く。

「規模を問わず〜のはずだ」など、少数の事例から仮説を広げない。

### 6. 読者への問いは、二択の判定ではなく点検項目

特定の解決策へ誘導せず、読者が自社で確認できる問いにする。

例：

* その工程を変えるには、誰の合意が必要か。
* どの作業に、誰の時間が使われているか。
* 既存の仕組みのうち、何を残す必要があるか。

問いは記事の分析に対応させる。毎回同じ点検項目を機械的に置かない。

### 7. 数字は、対象・期間・範囲を揃えて読む

組織全体の年間削減時間と、担当者1人の月間削減時間を、そのまま優劣にしない。

誰の、どの業務の、どの期間の数字かを確認する。内訳や測定条件が不明なら、その限界を残す。

単位の違いが記事の問いに関係する場合は掘り下げ、「自社では誰の・どの作業時間を減らしたいか」へ接続する。

### 8. 引用・件数は実データのみ

引用は原文と照合し、省略によって意味を変えない。事例本文にないことを事実として書かない。

掲載件数を使う場合は、「当サイトの掲載事例では」など対象範囲を明示する。掲載件数の多さを、市場シェアや顧客の選定理由に置き換えない。

### 9. 最後に、冒頭の問いへ答える

今回の2社から見えた分岐点を、根拠に見合った強さで述べる。

「会社によって違う」で終わらず、何の条件が違い、その違いが解き方とどう関係していたと読めるのかまで書く。

一方、公開された成功事例から、解決策の一般的な成功率や唯一の正解までは導かない。

## 5. 公開前の編集チェック

* 冒頭の問いに、結びまでで答えているか。
* 「同じ悩み」を共有タグだけで判断していないか。
* 解き方の違いを、製品名ではなく業務の変更箇所で説明できているか。
* 各「読み」に、根拠となる記述があるか。
* 会社の属性や掲載件数から、選定理由を作っていないか。
* 実際には両立する道を、二択として描いていないか。
* 共通点・第三の事例・数字の分析を、型を埋めるために追加していないか。
* 読者への点検項目が、今回見えた分岐点に対応しているか。
* タイトルや結論が、本文の根拠より強くなっていないか。

## 6. 公開手順

1. `python -c "import uuid; print(uuid.uuid4())"` でslugを生成する。
2. `content/articles/<uuid>.json` を既存記事のコピーから作成する。`format` は `"wakaremichi"`、`no` は連番とする。
3. サムネイル（5:3）を `public/thumbnail/<no>.png` に置き、`thumbnail` にパスを書く。
4. `npm run build` でビルドが通ることを確認する。
5. 公開前にプレビューで、引用・数字・章の順序・省略した章の扱い・サムネイルを確認する。
6. サイトの既定の公開フローで反映する。記事URLは `/articles/<uuid>`。一覧・トップへの自動掲載も確認する。
