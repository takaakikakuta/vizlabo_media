# 「導入の現場から」記事（genba型）の書き方

1社の事例を主役に、**同じ課題を扱う事例群と照らしながら、その解き方の特徴と、参考になる会社の条件を読み解く**フォーマット。

企画の起点は、**「事例を並べたら、どんな疑問が生まれたか」**。

wakaremichi型が複数の事例を並べて分岐を読むのに対し、genba型は一つの事例を軸に、周囲の事例から特徴や意味を浮かび上がらせる。

タイアップ（PR）にも編集記事にも使う。表示は `"sponsored": true / false` で切り替え、表記の出し分けはテンプレートが行う。

**スポンサーが決めるのは、光を当てる事例。事例群を読んで決めるのは、問いと結論。**

## 0. この記事の役割

### 事例記事との違い

| 記事               | 答える問い                                    |
| ---------------- | ---------------------------------------- |
| 事例記事（`/cases/…`） | この会社は、何に困り、何を導入し、どう改善したか                 |
| genba型の記事        | ほかの事例と照らすと、この取り組みにはどんな特徴があり、どんな会社の参考になるか |

成果や導入経緯は、記事の問いを解くために必要な部分を扱う。取り組みの全体像は事例記事に譲り、詳しい内容へリンクする。

元の事例との違いは、情報を重複させないことではなく、**その情報を使って答える問いが違うこと**で作る。

### この記事で避けること

* **選ばれた製品の「必然」を論証しない。** 公開情報だけから、ほかの選択肢が不適合だったと決めつけない。
* **周囲の事例を、スポンサーの製品を優位に見せるために使わない。** 各事例が扱った課題や工程の違いを示す。
* **製品の適合を診断しない。** 読者が自社との共通点や違いを確認する材料を渡す。
* **事例に書かれていない選定理由を作らない。** 状況に合う解き方だと読めることと、その理由で選んだことは区別する。

## 1. 軸事例と周囲の事例を選ぶ

### 編集記事の場合

次の条件を満たす軸事例を探す。

* 同じ課題を扱う、ほかの掲載事例がある。
* 事例群の中で注目する特徴を、具体的に説明できる。
* その特徴を読むための課題・施策・成果の記述がある。
* 読者が自社との共通点や違いを確認できる。

### タイアップの場合

スポンサーの事例を軸にする。ただし、**何を問いにするかは、周囲の事例を読んでから決める**。

先に「この製品が最適だった」という結論を置き、その裏づけになる事例だけを集めない。

公開情報だけでは問いを解けない場合は、追加取材で確認するか、根拠のある別の問いに変える。追加取材で得た情報は、公開事例からの情報と区別する。

### 周囲の事例を探す

共有する悩みタグや `productCategory` を手がかりに候補を探し、本文を読んで関連性を確認する。

* 同じ課題に対して、異なる工程を変えた事例
* 同じ解き方を、異なる業種や規模で使った事例
* 軸事例と似た制約を持つ事例
* 軸事例の特徴だと思ったものが、ほかにも見られる事例

タグ数や掲載件数は探索の補助として使う。タグが多いこと、同じベンダーの事例が多いことだけで、記事化を判断しない。

軸事例と主要な参照事例について、全文を読む。

確認する項目：

```text
title / summary / challengeDetail / actions / results
```

必要に応じて原典も確認する。

## 2. 記事の問いを決める

軸事例と周囲の事例を読んだら、記事で解く問いを1文で書く。

例：

> 同じ請求書業務の改善なのに、経理の時間が減る事例と、現場の時間が戻る事例がある。何が違うのか。

> 同じ電子化でも、取引先の協力が必要な会社と、社内だけで進められる会社では、導入の進め方がどう違うのか。

「なぜこの製品がよかったのか」だけで終わらず、**事例群を参照するからこそ生まれる問い**にする。

### 問いを選ぶ基準

1. **ほかの事例を参照する意味があるか。**
   軸事例だけで同じ結論が書けるなら、事例群の使い方を見直す。

2. **本文の具体的な記述から答えを組み立てられるか。**
   規模や業種に対する一般的なイメージだけで説明しない。

3. **スポンサーの製品を使わない読者にも、判断材料が残るか。**
   課題の見極め方、変更する工程、必要な協力などを持ち帰れる問いにする。

4. **1本の記事で扱える範囲か。**
   最も材料がある問いを一つ選び、機能紹介や複数の論点を詰め込まない。

## 3. 執筆前に、事実と読みを整理する

各論点について、次の3つを分けてメモする。

| 区分      | 書く内容                             |
| ------- | -------------------------------- |
| 確認できる事実 | 課題、施策、明記された選定理由、成果、追加取材で確認した内容など |
| 編集部の読み  | 事実を結びつけた解釈。根拠となる記述も対応させる         |
| 分からないこと | 比較した候補、選ばなかった理由、成果の内訳、未記載の運用条件など |

**「この状況に合う解き方だった」と「この理由で製品を選んだ」は別である。**

選定理由が明記されていなければ、「〜だから選んだ」とは書かない。

また、軸事例の特徴は、参照した事例の範囲で説明する。「当サイトで参照した事例と比べると」と「市場で唯一」は意味が異なる。

## 4. 構成

### 基本の流れ

PR表記（`sponsored` の場合）
→ 扉（タイトル・サブタイトル・リード）
→ サムネイル
→ 一 同じ課題への、いくつかの道
→ 二 今回注目する会社
→ 三 この事例は、どこが特徴的か
→ 四 どんな会社の参考になるか
→ 五 自社と照らす
→ 元の事例・関連事例への導線
→ ポリシー表記

### 各パートの役割

**扉**

事例群から生まれた疑問を提示し、今回の会社に注目する理由を示す。

サブタイトルを「◯◯という必然があった理由」に固定しない。記事が扱う問いに合わせる。

**一 同じ課題への、いくつかの道**

周囲の事例を使い、同じ課題にどのような手の入れ方があるかを示す。

カテゴリの分布だけで終わらず、実際に変えた工程や運用を説明する。すべての選択肢を網羅したようには書かない。

**二 今回注目する会社**

軸事例の状況と取り組みを、問いに必要な範囲で紹介する。

課題だけでなく、分析の根拠になる施策・導入経緯・成果も扱う。全体の詳しい内容は事例記事へ渡す。

**三 この事例は、どこが特徴的か**

周囲の事例との違いや共通点から、軸事例の解き方を読む。

基本の流れは、次のとおり。

> 軸事例で確認できる状況・施策
> → 周囲の事例との違いや共通点
> → そこから何が読めるか

論点数は根拠に合わせる。3つの見出しを埋めるために、特徴を増やさない。

**四 どんな会社の参考になるか**

今回読めた特徴を、読者が確認できる条件に言い換える。

業種や従業員数だけでなく、負担のある工程、関係者、既存の仕組みなどを見る。条件が似ていることは、同じ成果や製品適合の保証ではない。

異なる条件では何を追加確認すべきか、公開情報だけでは判断できないことは何かも示す。

**五 自社と照らす**

記事で扱った条件に対応する点検項目を置く。

例：

* その業務に時間を取られているのは誰か。
* 確認・転記・移動・承認待ちのうち、負担はどこにあるか。
* 工程を変えるには、誰の協力が必要か。
* 既存の仕組みのうち、何を残す必要があるか。

最後に、冒頭の問いへの答えを短くまとめ、元の事例や関連事例へつなぐ。

## 5. 執筆の作法

### 1. 必然ではなく、特徴と条件を読む

「この会社の状況だから、ほかの道は候補から外れる」という消去法を基本形にしない。

どの工程に負担があり、何を変えたのか。その解き方を理解するために、どの条件が重要なのかを説明する。

### 2. 周囲の事例は、具体的な取り組みで参照する

「RPAは一点しか変えられない」「会計システムでは現場を改善できない」など、カテゴリ全体の能力を決めつけない。

比較するのは、参照した事例で実際に扱われた課題と施策である。

実際の比較検討が確認できなければ、「選ばれなかった道」ではなく「ほかの事例で採られた道」と呼ぶ。

### 3. 製品名を出さない場合も、参照元は明確にする

原則として、周囲の解決策は業務の変更箇所や解き方のカテゴリを中心に説明する。

ただし、競合製品名を出さないことを理由に、出典を曖昧にしたり、相手の取り組みを単純化したりしない。参照した事例を読者が確認できる導線を設ける。

### 4. 見立てには、根拠と限界を付ける

推理パートには、テンプレートで「編集部の見立て」の断り書きを付ける。

ただし、断り書きは根拠の代わりにはならない。各見立てに本文の記述を対応させ、事実・解釈・不明点を区別する。

結論でも、解釈を事実へ変えない。

### 5. 成果と導入経緯は、問いに必要な範囲で使う

成果の数字を大きく見せるために並べない。何が変わったかを理解する根拠として扱う。

数字は、対象・期間・範囲を確認する。業務全体の成果を、根拠なく一つの機能や施策だけの効果として説明しない。

### 6. 掲載件数を、製品評価や課題の大きさに置き換えない

「当サイトに同じベンダーの事例が24件ある」ことから、製品の成熟度、市場シェア、顧客の選定理由までは導けない。

同じ課題タグを持つ事例が多くても、市場全体での課題の発生率は分からない。

件数を使う場合は、集計範囲と対象を明示し、記事の問いに必要な場合だけ扱う。

### 7. 参考になる条件と、追加確認が必要な条件を書く

「条件が合わなければ別の製品がよい」とまで断定しない。

取引先の協力、連携するシステム、扱う書類など、条件が異なる場合に何を確認すべきかを示す。

### 8. 広告でも、問いと結論を根拠から決める

スポンサーの事例を中心に扱うことと、スポンサーに有利な結論を作ることは別である。

根拠のある特徴が見つからなければ、問いを変えるか、必要な情報を追加確認する。掲載件数や会社の属性から、推薦理由を補わない。

## 6. 自動データと書き下ろしの分担

| 要素           | 役割                   |
| ------------ | -------------------- |
| 同じ悩みを持つ掲載事例数 | 当サイト内で参照できる事例の広がりを示す |
| 解き方の分布       | 掲載データ上のカテゴリ構成を示す     |
| 同じベンダーの関連事例  | 追加で読める活用例を示す         |
| 関連する課題・タグ    | 読者がほかの事例を探す入口にする     |
| 記事の問い・特徴の分析  | 本文の根拠から編集部が書く        |
| 参考になる条件・点検項目 | 記事の分析に対応させて編集部が書く    |

自動集計は、分析の材料や回遊の入口として使う。製品の適合判定や「診断」には使わない。

### JSON・テンプレートとの対応

執筆フィールドは、次のとおり（本ガイドに合わせて移行済み。「必然」の論証を担っていた `necessities` / `necessitySummary` は廃止した）。

```text
title / subtitle / lead / paths / pathsNote / axisNote /
features / fitIntro / fitConditions / fitCaution / checklist / closing
```

章との対応は `README.md` を参照する。解き方カテゴリの内訳・同ベンダーの関連事例はテンプレートの自動集計で、範囲を明示した参考情報として表示される（適合診断としては表示しない）。

フィールド名・章の順序・自動集計の扱いを変更する場合は、スキーマ、テンプレート、`README.md` を合わせて更新する。

## 7. sponsoredフラグ

| 表示箇所 | `true`（タイアップ）           | `false`（編集記事）            |
| ---- | ----------------------- | ------------------------ |
| 題字横  | supported by ◯◯         | なし                       |
| バッジ  | Sponsored（記事・一覧・トップ）    | なし                       |
| 末尾   | 「本記事はタイアップ広告です（提供：◯◯）…」 | 「本記事は編集記事です（広告ではありません）…」 |

広告として受注した記事は `true`、編集記事は `false` を明示する。

**どちらでも、引用・数字・見立ての基準は変えない。** 引用と件数は確認できるデータのみを使い、解釈には根拠と限界を付ける。

PR表記は記事本文だけでなく、一覧・トップでも確認する。

## 8. 公開前の編集チェック

* 事例群から生まれた問いが、冒頭にあるか。
* 周囲の事例を参照したことで、軸事例の特徴が具体的に見えているか。
* 軸事例の要約だけで成立する記事になっていないか。
* 「必然」「最適」「ほかの道では解決できない」といった、根拠を超える表現がないか。
* 解き方のカテゴリ全体を、根拠なく否定していないか。
* 実際の選定経緯と、編集部による事後的な比較を区別しているか。
* 各見立てに、根拠となる記述があるか。
* 掲載件数を、成熟度や選定理由の証拠にしていないか。
* 成果の数字について、対象・期間・範囲が分かるか。
* 参考になる条件と点検項目が、本文の分析に対応しているか。
* 自動集計が、製品適合の診断に見える表示になっていないか。
* スポンサーの製品を使わない読者にも、判断材料が残るか。
* 広告の場合、PR表記と提供企業名が各表示箇所で確認できるか。

## 9. 公開手順

基本手順は `WRITING-wakaremichi.md` と同じ。

1. `python -c "import uuid; print(uuid.uuid4())"` でslugを生成する。
2. `content/articles/<uuid>.json` を作成する。`format` は `"genba"`、`no` は連番とする。
3. `sponsored` を `true` または `false` で明示する。
4. サムネイル（5:3）を `public/thumbnail/<no>.png` に置き、`thumbnail` にパスを書く。
5. `npm run build` でビルドが通ることを確認する。
6. プレビューで、章の構成・引用・数字・参照リンク・点検項目・PR表記を確認する。
7. サイトの既定の公開フローで反映する。記事URLは `/articles/<uuid>`。一覧・トップへの掲載と表示も確認する。
