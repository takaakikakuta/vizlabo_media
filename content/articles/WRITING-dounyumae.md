# 「導入前の日本」記事（dounyumae型）の書き方

1つの困りごとタグを対象に、該当する掲載事例の**「導入前」の記述**を読み、繰り返し現れる悩みの型と言葉を編むアンソロジー。

企画の起点は、**「同じ悩みの課題文を並べて読んだら、何が繰り返されていたか」**。

製品やベンダーではなく、導入前の職場で起きていたことを主役にする。読者に渡すのは、「うちだけではなかった」という発見と、自分の職場の症状に名前が付く体験である。

**引用で状況が伝わり、型の名前で自社の問題に気づける記事を目指す。** 件数や分布は、その体験を支えるために使う。

改善の取り組みは、終盤で次に読める事例への出口として紹介する。

## 0. この記事の性質と限界

### 素材の性質

素材は、ベンダーなどが公開した導入事例の課題パートである。

* 公開に向けて選択・編集された記述であり、職場の実態をそのまま記録したものではない。
* 導入・改善の取り組みが、成功事例として公開された会社の記録である。
* 未導入の会社や、公開に至らなかった取り組みは含まれない。
* 成功事例として公開されていても、すべての課題が解消されたとは限らない。

この性質は、冒頭または記事の説明欄で短く明示する。終盤の演出のために隠さない。

例：

> 本記事は、公開された導入事例のうち、導入前の課題に関する記述を集めて構成しています。職場全体の実態や、悩みの発生率を示す調査ではありません。

### 記事から言える範囲

引用や集計から言えるのは、**対象とした掲載事例で、どのような課題が記述されていたか**までである。

市場全体での発生率、深刻度の順位、すべての職場に共通する性質は導かない。「導入前の日本」というシリーズ名を、日本全体の代表性を示す根拠にしない。

### 企業の扱い

引用には原則として業種・規模を添え、企業名は本文で前面に出さない。出典リンクから、どの事例かを確認できるようにする。

これは匿名化ではない。特定企業の失敗談を暴くような見せ方をせず、公開された記述の文脈を保つ。

業種や規模が確認できない場合は推測で補わない。

## 1. テーマ（タグ）を選ぶ

次の条件を目安に候補を選ぶ。

* **該当事例が十分にある。** 30件以上を探索の目安とするが、件数だけで記事化を判断しない。
* **業種の広がりがある。** 特定業種に限られる場合は、対象範囲をタイトルやリードで明示する。
* **課題文が具体的である。** 作業、関係者、困る場面などが読み取れる記述がある。
* **複数の事例で繰り返される状況がある。** 抽象的な「効率化が必要だった」だけでは型を作らない。

候補タグの件数確認：

```bash
python3.11.exe -c "import json,collections; d=json.load(open('../vizlabo_media/data/cases.json',encoding='utf-8')); [print(n,t) for t,n in collections.Counter(t for c in d for t in c.get('tags',[])).most_common(15)]"
```

タグは探索の入口である。タグが同じでも、実際に同じ悩みを扱っているとは限らないため、本文で確認する。

## 2. 対象を確定し、課題文を全件読む

### 対象を記録する

読み始める前に、次を編集メモに残す。

* 対象タグ
* データの取得日または集計基準日
* 該当する事例IDの一覧
* 該当件数
* 重複登録や課題文の欠落などの確認結果

同じ導入事例の重複登録を、別の事例として数えない。対象から除外したものがあれば、その理由を残す。

### 課題文を全件読む

対象事例の `challengeDetail` を全件読む。**一部だけを読んで型を決め、その型に合う引用を探す順番にしない。**

`challengeDetail` は全体を読み渡す入口として使う。導入前後の区別や文脈が不明な場合は、事例のほかの項目や原典も確認する。

読みながら、次を分けてメモする。

| 区分         | 内容                      |
| ---------- | ----------------------- |
| 繰り返される言い回し | 複数の事例に現れる語や表現           |
| 繰り返される状況   | 言葉が違っても、似た作業や困り方を示す記述   |
| 型の候補       | 「その人が休むと、止まる」など、悩みの現れ方  |
| 引用候補       | 具体的で、状況が目に浮かぶ文章         |
| 型に収まらない記述  | 単独の悩みや、最初の分類を見直す材料      |
| 出典の性質      | 当事者の発言、記事の説明文、自サイトの要約など |

型は全件を読んだ後で整理する。読んでいる途中に立てた仮の分類は、必要に応じて変更する。

## 3. 引用を選び、原典と照合する

### 当事者の発言と説明文を区別する

引用候補は、原典で文章と文脈を確認する。

| 素材             | 扱い                             |
| -------------- | ------------------------------ |
| 原典に掲載された当事者の発言 | 発言であることが分かる形で引用する              |
| 原典の記事による説明文    | 「事例記事では〜と説明されている」など、説明文として引用する |
| 自サイトで作成した要約    | 要約として扱う。当事者の声や原典の実文引用として表示しない  |

**自サイトの要約を、そのまま表示しても当事者の実文引用にはならない。**

### 引用のルール

* 記事の分析に必要な範囲を引用し、出典リンクを付ける。
* 省略や接合によって意味を変えない。
* 離れた文章をつないで、一続きの発言に見せない。
* 導入後の記述を、導入前の状態として引用しない。
* 記述されていない感情を補わない。
* 業種・規模は出典の時点を確認し、現在の情報と無自覚に混ぜない。

引用だけで状況が伝わらない場合は、確認できる背景を短く添える。

## 4. 決まり文句（phrases）— 言葉の反復を集計する

言い回しの件数は、`phrases` に `label` と `pattern` を設定して機械集計する。

ただし、**言葉の反復と、悩みの反復は別である。** 同じ言い回しが多い理由には、同じベンダーや書き手の表現の癖も考えられる。

`phrases` は記事の補助として使い、型の根拠は文章の意味から判断する。

### 集計単位を揃える

* 数えるのは出現回数ではなく、**その表現を含む異なる事例の数**とする。
* 同じ課題文に複数回出ても、1事例として数える。
* 集計対象のフィールドを固定し、原典全体の集計と混同しない。
* 要約文を対象にする場合は、「当サイトの課題要約に含まれる表現」と明示する。
* 自動的に生成・整理した要約の語彙を、そのまま当事者に共通する言葉として扱わない。

### 一致箇所を確認する

集計後は、一致した文章を一覧で確認する。

* 「勘」が「勘定」に当たるなど、別の意味を拾っていないか。
* 「属人化していない」など、否定の記述を症状として数えていないか。
* 導入後の説明を拾っていないか。
* 特定のベンダーや定型文に一致が集中していないか。
* 意味の異なる言葉を一つの `pattern` にまとめていないか。

3件未満の表現は表示しない仕様を基本とする。表示させるために検索条件を広げない。

件数は「対象◯件の課題文のうち」という範囲の数字である。症状の発生率や深刻度の順位として見せない。

## 5. 型（types）— 繰り返される状況に名前を付ける

### 全件を分類し切る必要はない

型は、全件を読み通したうえで見つかった反復を示す。

* 型の数は材料に合わせる。
* すべての事例を分類する必要はない。
* 一つの事例が複数の型に当てはまってもよい。
* 型に収まらない記述を、無理に押し込まない。
* 各型が何件の異なる事例で確認できたかを、編集メモに残す。

一つの印象的な記述だけで「繰り返される型」としない。

### 型の名前

型の名前は、状況が浮かぶ短い文にする。

例：

* その人が休むと、止まる。
* 辞めてから、分からないことが分かる。
* やり方が、人数分ある。

引用の言葉に寄せてもよいが、**編集部が付けた見出しと、実際の引用を混同させない。**

当事者を責める名前や、原文より深刻に見せる名前を付けない。

### 引用と本文

各型には、代表的な引用を1〜2本置く。

* 同じ事例を、複数の型の代表引用として繰り返さない。
* 可能であれば、業種や規模の異なる事例を組み合わせる。
* ただし、業種を散らすために弱い引用を選ばない。

型の本文は2〜3文を目安にする。

> 引用に共通する状況
> → 編集部による短い整理

引用から確認できることと、編集部の解釈を分ける。原因分析や解決策の説明へ広げすぎない。

## 6. 規模・分布の節（scaleBody）

この節では、異なる業種や規模の事例に、どのような記述の重なりが見られたかを書く。

「最小◯名〜最大◯名」などの数値は、対象事例の範囲と人数の定義を確認して使う。正確な人数と人数帯、単体とグループ全体を混在させて比較しない。

### 書けること

> 今回読んだ掲載事例では、異なる規模の会社に「担当者が不在だと処理が進まない」という記述が見られた。

### 書かないこと

> 規模は関係ない。
> どの業界も同じ問題を抱えている。

異なる規模に同じ記述があっても、規模との関係がないことは示せない。

業種・規模の分布から、悩みの原因や発生率を説明しない。分布だけでは読みが深まらない場合は、節を短くするか省略する。

## 7. 出口（reprieveIntro）と結び（closingLines）

### 改善の取り組みは終盤で紹介する

素材が導入事例であることは冒頭で示し、具体的な改善の取り組みは終盤で初めて紹介する。

「実は全社が解決していた」と反転させず、**ここまで読んだ悩みに、各社がどう手を入れたのか**へつなぐ。

### 出口は「変えたこと」から示す

製品カテゴリだけでなく、記事で扱った症状に対応する変更内容を入口にする。

例：

* 手順を共有できる形にした。
* 情報を一か所に集めた。
* 特定の人に集中していた作業を分担した。

これらの説明も、各事例の施策を確認して書く。「この型にはこの製品」と一対一に割り当てない。

関連事例やタグページへ渡し、詳しい解決策はリンク先で読めるようにする。製品カテゴリの分布は、必要に応じて補助として置く。

### 結び

結びは1〜2行を目安にする。職場の状況を見つめ直す言葉で締める。

感情に訴えてよいが、記述されていない苦しさを代弁したり、必ず解決すると約束したりしない。脅しや製品への強引な誘導にしない。

## 8. 構成

基本の流れ：

扉（タイトル・リード・素材の説明）
→ サムネイル
→ 対象事例の範囲
→ 繰り返される言葉（必要な場合）
→ 悩みの型と引用
→ 業種・規模を越えた記述の重なり（必要な場合）
→ 各社が変えたこと
→ 結び・関連事例への導線

中心は、型と引用である。集計や分布の説明が長くなり、引用にたどり着くまで時間がかかる構成を避ける。

章番号や節の数は、実際に掲載する内容に合わせる。「四章に出口を置く」など、固定の章数を優先しない。

## 9. 自動データと書き下ろしの分担

| 要素             | 出どころ・確認方法                          |
| -------------- | ---------------------------------- |
| 対象事例数・業種数      | 確定した対象事例から自動集計                     |
| 言い回しを含む事例数     | `phrases` の `pattern` で集計し、一致箇所を確認 |
| 引用本文・出典リンク     | 原典と照合済みの引用データから描画                  |
| 業種・規模          | 事例データから描画し、出典時点と定義を確認              |
| 型の名前と本文        | 全件を読んだうえで編集部が書く                    |
| 規模・分布の読み       | 確認できる記述の範囲で編集部が書く                  |
| 各社が変えたこと       | 施策の記述を確認して編集部が整理する                 |
| 関連事例・タグページへの導線 | 対応するデータから生成                        |
| リード・結び         | 編集部の書き下ろし                          |

自動表示は、内容の正しさを保証するものではない。引用・集計条件・出典との対応は、公開前に確認する。

### JSON・テンプレートとの対応

執筆フィールドは、次のとおり（本ガイドに合わせて移行済み。`quoteIds` による課題要約の自動表示、`scaleBody`「規模は、関係ない」、`reprieveIntro` の反転演出は廃止した）。

```text
axisTag / title / lead / sourceNote / baselineNote / phrases（任意） /
types（quotes: caseId + text + kind） / spreadBody（任意） /
exitsIntro / exits / closingLines / thumbnail
```

* 引用は `types[].quotes[].text` に原典照合済みの本文を入れ、`kind`（speech＝当事者の発言／article＝事例記事の記述／summary＝当サイトの課題要約）を明示する。テンプレートが種別ラベルと出典リンクを付ける。
* `baselineNote` に集計基準日・読んだ件数・照合の経緯を書く（対象範囲の節に表示される）。
* 決まり文句は「表現を含む事例数」で自動集計される（同じ課題文に複数回出ても1事例。3件未満は非表示）。
* `phrases` と `spreadBody` は任意。省略すると章ごと消え、章番号は自動で詰まる。
* 「各社が変えたこと」は `exits`（label＝変更内容、body＝施策確認済みの説明、caseIds＝関連事例）で表示される。解き方カテゴリの分布は範囲明示つきの補助として自動表示される。

フィールド名・章の扱いを変更する場合は、スキーマ・テンプレート・`README.md` を合わせて更新する。

## 10. 公開前の編集チェック

* 対象事例と集計基準日を記録したか。
* 重複登録や課題文の欠落を確認したか。
* 対象の課題文を全件読んでから、型を整理したか。
* 各型が、複数の異なる事例の記述に基づいているか。
* 分類し切るために、無理な型や引用を作っていないか。
* 引用を原典と照合したか。
* 当事者の発言、記事の説明文、自サイトの要約を区別しているか。
* 業種・規模の表記と出典時点は正しいか。
* `pattern` の一致箇所を確認したか。
* 否定形、別の意味、導入後の記述を数えていないか。
* 言葉の一致を、そのまま症状の発生率として扱っていないか。
* 特定ベンダーや定型文への集中を確認したか。
* 掲載事例の観察を、日本全体の話に広げていないか。
* 素材が公開された導入事例であることを、冒頭付近で示しているか。
* すべての課題が解消されたと決めつけていないか。
* 出口の説明が、実際の施策に基づいているか。
* 結びが、脅し・感情の代弁・解決の保証になっていないか。
* 引用と型が中心にあり、集計報告に寄りすぎていないか。

## 11. 公開手順

基本手順は `WRITING-wakaremichi.md` と同じ。

1. `python -c "import uuid; print(uuid.uuid4())"` でslugを生成する。
2. `content/articles/<uuid>.json` を作成する。`format` は `"dounyumae"`、`no` は連番とする。
3. 対象事例・集計条件・引用照合の編集メモを残す。
4. サムネイル（5:3）を `public/thumbnail/<no>.png` に置き、`thumbnail` にパスを書く。
5. `npm run build` でビルドが通ることを確認する。
6. プレビューで、集計範囲・件数・引用・出典・型・結び・関連事例への導線を確認する。
7. サイトの既定の公開フローで反映する。記事URLは `/articles/<uuid>`。一覧・トップへの掲載も確認する。
