# 「事例でわかる技術用語」（yougo型）の書き方

「〇〇とは」で検索した人向けに、用語の説明と、その用語で課題を解いた事例を1記事にまとめるコーナー。説明だけのサイトとの差は事例が付いていること。狙いは検索流入。
`format` は `"yougo"`、`series` は `"事例でわかる技術用語"`。事例セレクションとは別の連載で、一覧は `/terms`、記事は `/terms/<slug>`（トップにも別のセクションで出る。`/articles` の一覧には載らない）。連番 `no` も事例セレクションとは別に数える（サムネイルは `public/thumbnail/yougo-<no>.jpg`）。

## 0. 性質と限界

- 用語の説明は一般的な仕組みの範囲にとどめ、数字を書かない。事例の数字・事実は各事例の `results`・`challengeDetail`・`actions` に記録された公開情報だけを使う。
- 記事の目線は作り手ではなく「自社の課題で同じことがないか」を考える読者。製品の優劣は書かない。
- 事例セレクションと事例が重なってもよい。

## 1. 選定

- 候補は `data/cases.json` を用語（製品名・title・summary・actions・tags）で引く。掲載禁止ベンダー（`data/blocked_vendors.json`）・`hidden` の事例は使わない。
- リンクのみの事例（`linkOnly: true` の事例と、`data/link_only_vendors.json` のベンダーの事例）は候補に入れてよい。記事では社名・規模・数字が出ず、掲載元へのリンクだけになるので、選んだら最初から `items[].linkOnly.body` を書く（4節）。読みどころを本文で書けない分、1記事に入れるのは1本までにする。
- 本数は事例セレクション（[WRITING-sen.md](WRITING-sen.md)）と同じで、**多ければ10本、少なければ5本**（2026-11-16 に変更。それまでは3本か5本）。目安も同じで、10本 = 素材級15件以上・うち数字あり7件以上・提供元5社以上、5本 = 素材級10件前後・うち数字あり4件以上。10本ぴったりでは選べないので、10本は15件以上から組む。業種で絞った用語（ERP × 製造業 など）は [TERMS.md](TERMS.md) の業種別の行で見る。数字のない事例は10本で3本まで、5本で1本まで。
- 条件が違う会社を選ぶ。業界・企業規模・抱えていた課題のうち、どの2社を比べても最低2軸が異なること。全業種の記事は、5本なら業界3つ以上、10本なら業界5つ以上にまたがらせる（業種で絞った記事は、事業の違いと規模・課題で散らす）。同じ提供元の事例は5本なら1本まで、10本なら2本まで。
- 選定理由（なぜこの組み合わせか、何が分かれ目か）を先に短く書いてから本文に入る。

## 2. 構成とフィールド

| フィールド | 記事上の場所 |
|---|---|
| `term` / `title` | 用語と見出し。見出しは「{用語}とは｜{N}つの事例でわかる」（Nは10か5。業種で絞った記事は「{業種}の{N}つの事例でわかる」） |
| `lead` | 2〜3文。**用語の定義は書かない**（定義は `definition` の1段落目だけ。両方に書くと「一 {用語}とは」の直前で同じ説明を二度読ませることになる）。1文目は用語の一言の言い換え（例: RFIDは、電波で読める荷札だ）、2文目は検索した人が抱えている疑問（似た言葉との違い・自社に要るのか）、3文目は「この記事では…を先に説明し、…の違うN社の事例を添えた」で事例の並びを紹介する。社名・規模・成果の数字は書かない |
| `description` | meta description（120字以内）。`app/articles/[slug]` が検索結果向けに使う |
| `thumbLine` | サムネ用の一行要約（表には出さない。SNS・画像制作用） |
| `definition` | 「一 {用語}とは」（300字程度・1段落。前半3〜4文で、用語が何か・似た言葉との違い・どの手作業を置き換えるかを専門用語を使わずに書き、後半2〜3文で使いどころを業種や場面で2つほど挙げ、効き目が何で決まるかで締める。業種ごとの使いどころを長く並べる第2段落は置かない） |
| `fitNote` | 「一」の末尾。向いている仕事・向かない仕事を1〜2文で（箇条書きにしない） |
| `figure` | 任意。「一」の末尾に置く解説図。`public/terms/yougo-<no>.webp`（3桁ゼロ埋め）に置き、`src`・`alt`・`width`・`height` を書く。`alt` は図の要点（構成・違い・使いどころ・向き不向き）を文で |
| `items[]` | 事例。見出し（導入企業名 × サービス名）・業種・規模・提供元・成果チップ・事例リンクは自動（事例ページで要約を見るリンクと、提供元の元記事への外部リンクの二段。事例セレクションと同じ）。書くのは `label`（4〜8字の一言ラベル。例: 店舗の棚卸）、`body`（**あらすじは書かない。** 「この事例は用語のどの使い方か」と「ほかの項目と何が違うか」だけを2〜3文・80〜130字で。困りごと → 施策 → 成果の経緯は元記事と事例ページで読めるので繰り返さない。成果の数字は成果チップにあるので言い直さない。数字のない事例は起きた出来事に1つ触れる。ほかの項目と比べるときは番号で指す。事例セレクションの `body` と同じ規範。1文目から位置づけか比較で入り、「〇〇が〜した事例。」という誰が何をしたかの要約で始めない。経緯を順に述べない。違いを言うのに必要な事実に1つ触れるのはよい。編集の目線の言い回し（「〜で記録されている」「〜として読める」「読みどころ」）と、比較を二度言う形（「ほかの項目が…中で、…点がほかにない」）は使わない）、`hitokoto`（読者が自社に当てはめられる一言。用語の効き目が何で決まるかを言い切る。技術用語だけにある欄で、ここが本体）。製品名が長いときは `service` で見出しの表記を短くできる |
| `relatedTerms[]` | 「二 関連する用語」。用語記事があればそのURL、無ければ困りごとタグ（`/tag/…`）や製品カテゴリ（`/product/…`）のページ |
| `relatedSlugs[]` | 「二」の「あわせて読む」。関連する事例セレクションの slug |

説明は「一」だけに置く。向き不向きの箇条書きや、事例の後の「分かれ目」「まとめ」は置かない（2026-11-07 に外した。説明が3層になると読まれない）。自社に近い事例を選ぶ手がかりは、各事例の `label` と `hitokoto` が担う。

締め（AI事例サジェスト＋メルマガ登録、掲載サービス一覧と一括問い合わせ、ポリシー表記）はテンプレートが出すので書かない。

## 3. 各項目の書き方

- `label` は仕事の名前（店舗の棚卸、機器の貸出管理、患者の本人確認）。業種名や社名にしない。
- `body` は2〜3文・80〜130字。書くのは「用語の中でのこの事例の位置づけ」と「ほかの項目との違い」だけで、困りごと → 施策 → 成果の経緯は書かない（事例セレクション [WRITING-sen.md](WRITING-sen.md) 2節と同じ規範。経緯は元記事と事例ページで読める）。1文目から位置づけか比較で入り、「〇〇が〜した事例。」という要約で始めない。ほかの項目は番号で指す。比較は半分くらいの項目で十分で、残りは用語との関係を書く。事例データ（課題文・施策・成果）の範囲で書き、盛らない。見込み値・範囲の限定は本文で明示する。
- 成果の数字は `body` に書かない（成果チップにある。違いを言うのに必要な事実として1つ触れるのはよい）。数字のない事例は、起きた出来事に1つ触れる。
- `hitokoto` は読者に向けて言い切る。「〜1本。」「〜を示す事例。」のような編集者の説明は書かない。
- 事例セレクションの歯止め（WRITING-sen.md 7節）をそのまま守る。ダッシュは1記事2回まで、本文の「」は固有名詞・製品名・引用だけ。
- 公開前に `.claude/skills/yomiyasu` のリンターを通す。

## 4. リンクのみに耐える書き方

`title`・`lead`・`definition`・`fitNote`・`label` には社名・規模・成果の数字を書かない（事例が `linkOnly` になっても書き直さずに済む水準）。
事例が `linkOnly` になったら（または最初からリンクのみの事例を選んだら）`items[].linkOnly.body`（企業名・規模・数字を伏せた1〜2文）を書く。確認は `node scripts/link-only/check.mjs --as-if <記事ファイル名>`。

書いた後は `node scripts/verify/yougo-check.mjs <記事番号>` で、body・hitokoto の数字が事例データ（`data/cases.json` の title・summary・課題・施策・results・scale・規模）にあるか、長さ・「」・「唯一」の回数を機械的に照合する（事例セレクションの sen-check と同じ役割）。**数字は事例データにあるものだけを書く。** 元記事を読んだ記憶や計算で出した数字は書かない（2026-11-21 に #7 の旧 body で、データが「2時間半→10分」の成果を「2か月から10日」と書き、データにない「16年使った」を書いていたのが見つかった。あらすじを長く書くほど、データにない事実が混ざる）。

## 5. 公開手順

1. `python -c "import uuid; print(uuid.uuid4())"` で slug を生成し、`content/articles/yougo-<no>-<用語>.json` を置く（`draft: true` で下書き）。
2. `npm run build` が通ることを確認し、`node scripts/inventory/inventory.mjs` で INVENTORY.md を更新する。
3. 公開するときは `draft` を消し、`publishedAt` を公開日にする。記事URLは `/terms/<slug>`（`/articles/<slug>` で開いても `/terms` へ転送される）。

- 2026-11-27：3節の `body` の書き方が旧規範（困りごと → 変えたこと → 結果の順、数字は末尾）のまま残り、11/21 に改めた2節と正反対の指示が同居していたので、2節に合わせて書き換えた。2節の「1文目：誰が何をした事例か」も、事例セレクションと同じ「1文目から位置づけか比較で入る」に改めた。#14・#15 の body を同日に書き直した（この2本は 11/22〜24 に書かれ、経緯を順に述べる旧い形に戻っていた）。#1〜#13 は 11/21 に書き直してあり、「〜した事例。」の書き出しだけが残っている。
- 2026-11-27：#2〜#15 の `definition` を300字前後・1段落に縮めた。それまでは第2段落に「使いどころは業種で…」を500〜700字で並べていたが、「一」が長いと事例まで読まれない。使いどころは2〜3文に圧縮し、残りは `fitNote` と各事例の `label`・`hitokoto` に任せる。
- 2026-11-21：`items[].body` の役割を「あらすじ」から「用語の中での位置づけと、ほかの項目との違い」に改めた（事例セレクションの 11/18 の改訂と同じ理由。事例カードを二段にして元記事と事例ページに直接行けるようになり、あらすじが3か所に並ぶため）。`hitokoto` はそのまま残す。#1〜#13 の body を同日から順に書き直した。
